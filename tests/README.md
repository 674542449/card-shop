| 问题 | 修复与验证 |

## 六项运行完善与回归

关闭、缺货及优惠名额冲突订单收到正确渠道和金额的付款时，先在事务内记录付款回执及待核对原因，再加入去重告警；错误渠道或不足额不会留下有效回执。后台可筛选、查看原始流水、金额、时间和处理原因。三套模板的付款按钮、继续支付入口和轮询均识别待核对付款，避免重复支付。

后台设置使用跨路由存活的单个保存队列，卸载、重试和测试邮件共享串行请求；旧请求不能覆盖新编辑，失败保留最新输入，存在待保存内容时提示退出。Node 测试覆盖异步请求交错、离页刷新、失败重试和同步异常。

API 查单迁移为 POST `/api/v1/orders/{order_no}/query`，邮箱与密码只接受请求正文；旧 GET 返回 405，响应禁止缓存。Nginx 访问日志只记录路径，省略 query、Referer、正文与 Authorization。令牌新增请求、下单、待付订单和占用卡密额度；两进程同时下单验证行锁保护订单数及占用数量上限，换 IP 不绕过令牌额度。到期但仍未释放卡密的订单继续占用额度，测试验证实际过期事务释放库存后才恢复下单额度。

支付事务只写数据库通知队列，常驻 `notifications:send --work` 发送邮件和 Telegram，最多 5 次尝试，失败可在后台重新入队。测试覆盖提交/回滚、进程中断租约、重试退避、补发去重、TG HTTP 200 但业务拒绝、邮件内容转义，以及常驻进程切换和清空 SMTP 配置。并发支付回调验证仅发货和入队一次；发送服务与写入完成标记之间崩溃仍可能导致通知重复，见 README 的说明。

商品新增可关闭的低库存阈值，概览、商品筛选和每分钟 TG 通知共用规则。同一轮低库存提醒去重，补货越过阈值后恢复提醒。界面复验包括主商城 12 件低库存筛选、商品阈值表单，以及隔离商城的失败通知重试、异常付款原始回执、等待发送状态、设置编辑后导航并返回、四项令牌默认额度（未创建凭据）。补修手机菜单切换页面后未收起的遮挡问题，并实测已收起。截图位于 `.local/operational-order-review.png`，设置测试结束后已还原商城名称。数据迁移前已备份，主商城保留原有 49 件商品及 180 笔演示订单。

## 运行

本地 Windows 开发环境：

```powershell
php vendor/phpunit/phpunit/phpunit --no-progress
npm.cmd --prefix admin-frontend test
```

`phpunit.xml` 配置独立 PostgreSQL 数据库 `cardshop_testing`（端口 15432）和 Redis 数据库 10、11（端口 16379），数据库用户名及密码继承本地 `.env`。测试数据库已在本机创建。其他机器需要先建立测试数据库，按环境调整连接配置。

测试会迁移、清理测试数据库和 Redis 缓存库，请只使用专用测试实例。`TestCase` 在执行迁移前检查数据库名称与 Redis 库编号，拒绝使用当前开发商城的数据库及缓存库。若本地曾执行配置缓存，先运行 `php artisan config:clear`，让测试环境配置生效。

后台源码变更后需要执行 `npm run build`（目录 `admin-frontend`），并用 `docker/php/spa-stamp.sh` 更新 `public/admin-assets/.build-stamp`。本次构建产物已更新。
